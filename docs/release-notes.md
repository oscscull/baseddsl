# Based 0.1.12 release candidate

This is the versioned evaluation candidate for the v1 readiness checklist. A tag
and public release are created only after the owner approves that checklist.
Dry-run artifacts identify their exact source commit and dirty state in
`manifest.json`; they do not establish a published release.

## Install and pin

Use the archive matching the supported target in the installation guide, verify
its SHA-256 checksum, and install `based` and `based-lsp` together. Each reports
its version and source commit with `--version`. Pin library dependencies to the
same published source tag; keep application Cargo.lock committed. Registry and
marketplace publication are not part of this initial distribution route.

## Regenerate and upgrade

Generated clients are generator-owned. When changing the compiler/runtime
version, pin the matching library source, regenerate the client with
`based gen all`, and run `based gen all --check` plus the application's lint/build
and typed-operation tests. Keep generated files in an isolated `generated/`
directory behind a small `include!` wrapper. The optional OUT_DIR prototype is
not the starter default after the measured build-cost gate.

This candidate consolidates changes to scalar codecs, nullable/nested JSON,
typed entity IDs, exact decimal handling, generated wire/embedded transports,
transaction/guard behavior and artifact lifecycle. Existing clients from earlier
experimental revisions must be regenerated together with the runtime upgrade;
API or wire-shape changes require adapting the application's call sites and
validation. Do not independently upgrade only the compiler or only the runtime.
Read the generated diff and the reference for the operations the app uses.

Client generation never applies a database migration. Generate and review
migration SQL separately, verify the history, then explicitly apply migrations
to the intended database. Preserve backups and rollback plans appropriate to
that deployment. Pinning an older binary/library does not reverse an applied
migration or undo persisted data.

## Candidate behavior and API changes

### Conditional helpdesk close

The helpdesk's close transition now requires a resolved ticket in the database
UPDATE itself. A concurrent reopen after guard approval leaves the ticket open
and returns `404 not_found`. Preflight denials remain `403 guard_denied`.
Shape-returning updates with direct conditions on assigned fields and an explicitly
bound unchanged primary key check whether the write matched before reading the
result by that key. The
condition can change during the update without preventing a successful read-back.

### Generated Rust decimal type

Generated clients now use their `client::Decimal` type, backed by
`bigdecimal::BigDecimal`, for every BSL `decimal(p,s)` field and parameter.
Existing consumers that construct or annotate `rust_decimal::Decimal` values
must switch to `client::Decimal` and add `bigdecimal = "0.4"` to their
dependencies. Parse decimal literals with `"19.90".parse::<client::Decimal>()`.
This is a generated Rust API change; regenerate checked-in clients together
with the consuming application code.

Decimals remain JSON strings on the wire and `type: string, format: decimal`
in OpenAPI. The new client serializer emits plain notation, preserving exact
numeric value and the parsed scale. A database's declared DECIMAL scale may
normalize the returned spelling. SQLite columns generated by Based use TEXT
storage, which preserves the decimal string; SQLite expressions that cast it
to a numeric storage class have SQLite's usual floating-point limits and are
outside that storage guarantee.

## SQLite engine safety floor

The workspace/native tools and runtime SQLite feature now require
`libsqlite3-sys` 0.37.0 / bundled SQLite 3.51.3, containing the upstream WAL-reset
corruption fix. This fits SQLx 0.9's supported binding range. Rebuild/update the
embedded application's runtime and lockfile too; upgrading only the CLI does not
replace the engine inside an old executable. The actual linked engine is checked
in runtime tests and extracted native smokes. See the
[upgrade guide](upgrading.md) and [readiness decision](v1-readiness.md). No schema
migration or automatic repair of pre-existing corruption accompanies this update.

## Known limitations

Embedded applications still load/supply runtime schema assets and configure a
backend and production ID generator. The standalone service requires a trusted
authentication edge, sanitized context headers and restricted direct access;
review the deployment guide before exposing it. Guard callbacks are optional
operator-configured integrations. The durable database idempotency store has a
reviewed provisioning lifecycle; the memory store cannot cover restarts or
multiple processes. See the deployment and generated-consumer contracts for
precise tested boundaries.

The Cargo helper is an optional prototype. The initial release has no automatic
binary updater/download, marketplace installer or automatic migrations. The
support matrix covers native release artifacts; other platforms can evaluate
pinned source builds without a prebuilt-binary support promise.
