# Embed a typed access layer in a small Rust app

Start with one `Item` model, an optional parent relation to another `Item`, and an
owner scope. Create a parent and child, read their nested projection, handle a
missing scoped lookup, then rename a database field without losing data or
breaking the public client field. There is no login system or web framework.

## Install and create

Install matching [versioned tools](installation.md) from a release or candidate
artifact set containing the current tutorial starter. Source evaluation uses an
exact Git revision; do not substitute floating `main`. Embedded apps require
Rust 1.94+, Cargo/Git, and platform C build tools. SQLite is bundled with the
selected Rust driver; you do not need Docker or a database server.

In an **empty directory**:

```sh
based init --mode embedded
based migrate apply --database-url local.db
cargo run
```

No manual source edits are needed for this first run. The database is a real
`local.db` file, not an in-memory database. Init checks and prepares an initial
migration offline; the second command applies it explicitly. `cargo run` loads
the schema, opens the file, and calls the generated in-process client.

Output contains:

```text
created: {"id":"<uuid>","name":"Hello Based","parent":{"id":"<parent-uuid>","name":"Parent"}}
read: [ ... the same child and its parent ... ]
lookup: not found in this owner's context
```

Row order follows the UUID sort, so the parent need not appear first. Repeating
`cargo run` adds another parent/child pair; it does not reset or erase existing
rows. Assertions live in the separate smoke gate, not the application example.

## Read the short files

The files generated by init are the tutorial. Their canonical sources live under
[`crates/based-cli/starter/`](../crates/based-cli/starter/); the initializer, this
lesson, and CI use that same source rather than a second example copy.

| File in your project | Single purpose | Canonical source |
|---|---|---|
| `schema/item.bsl` | Declare the model, optional parent relation, owner scope, projection, and access operations | [Schema](../crates/based-cli/starter/schema/item.bsl) |
| `src/main.rs` | Wire checked schema, connection, and production UUID generator into the engine | [Wiring](../crates/based-cli/starter/embedded/main.rs) |
| `src/database.rs` | Open the local file or the caller's server connection | [SQLite connection](../crates/based-cli/starter/embedded/sqlite.rs) |
| `src/session.rs` | Supply trusted host identity for the local example | [Context source](../crates/based-cli/starter/embedded/session.rs) |
| `src/demo.rs` | Create related items and read the typed projection | [Typed calls](../crates/based-cli/starter/embedded/demo.rs) |
| `src/lookup.rs` | Handle optional lookup results and client errors | [Lookup](../crates/based-cli/starter/embedded/lookup.rs) |
| `based.toml` | Configure the dialect, schema root, and generated destinations | [Manifest template](../crates/based-cli/src/init/manifest.rs) |
| `Cargo.toml` | Pin the library source and declare ordinary consumer dependencies | [Dependency template](../crates/based-cli/src/init/cargo.rs) |

`generated/client.rs` and `generated/schema.sql` are generator-owned outputs;
`migrations/` is reviewable, stored migration history. Do not hand-edit the client
or place it among files that normal `cargo fmt` traverses. The small `include!`
wrapper keeps it outside ordinary application formatting. There is no build
script and no implicit compiler invocation during a Cargo build.

The application and Cargo manifest can be copied outside the repository: its
library URL is public Git source pinned to the CLI's source commit, with no
checkout-relative dependencies. Commit the consumer's `Cargo.lock` after its
first build. Install/upgrade the matching CLI and update source pins deliberately.

## Understand typed calls and context

`ItemView` exposes the item's ID/name and an optional nested parent. Generated
`Id<entity::Item>` values distinguish entity IDs from arbitrary strings. A created
parent supplies the child's typed parent input; absent parents use `None`.

The `Author` scope binds the model's `owner` column from `$ctx.owner`. Creates set
it from context; reads and lookups filter by it. Call input and context are
separate generated types. The Rust app gets context from `Session`, not from an
unverified body/header. The fixed owner UUIDs in `Session` are local example
identities, **not credentials** and not the generator for item IDs. Item IDs use
`UuidGen`.

In a real application, replace the local session constructors with your existing
authentication result. Validate that result before constructing context. The
engine enforces the scope using the supplied context; it does not authenticate
your end user. See [authentication and scopes](reference.md#auth--scope) for the
language contract.

`item_by_id` returns `Result<Option<ItemView>, ClientError>`. `Ok(None)` is an
ordinary absent/invisible lookup, not a transport failure. The example handles
it without a panic. For `Err`, `lookup.rs` inspects `kind()`, the stable `code()`,
and optional HTTP `status()` before returning the error to the caller. Other
operations propagate errors with `?`; production handlers can translate those
classes into their own responses.

## Rename a field without losing data

Keep your populated `local.db`. In `schema/item.bsl`, make these edits:

1. Change the model field `name: text` to `title: text @was("name")`.
2. In `ItemView`, change its bare `name` to `name = title` and its nested
   `parent { id, name }` to `parent { id, name = title }`.
3. In the create assignment, change `name = $name` to `title = $name`.
   Keep the public parameter named `name`.

Then run:

```sh
based check
based gen all
based migrate gen . rename_item_title
based migrate verify
based migrate render . --number 2
```

Review `migrations/0002_rename_item_title/up.mig` and the rendered SQL. The stored
step should rename the column, rather than dropping and recreating its contents.
`migrate gen` consumes the captured `@was` hint from source after recording it in
history. Generation and planning have **not** changed your database yet.

Apply and run again:

```sh
based migrate apply --database-url local.db
based gen all --check
cargo run
cargo fmt --check
cargo clippy -- -D warnings
```

Existing IDs, owner values, names, and parent links are preserved. The public
output field and input parameter remain `name` through explicit projection and
assignment, so no consumer source edit is required. Regenerate even when the
client reports `current`: unchanged public contracts can produce unchanged Rust
while SQL and migration artifacts change.

Changing public shape/parameter names instead would change the generated Rust
API; update its call sites deliberately. Applied migration history remains
immutable. See [migration syntax](reference.md#migrations) and
[artifact lifecycle](generated-artifacts.md) for the separate contracts.

## Rerun, start fresh, or use a server

Rerun normally to retain data. For a fresh learning run, choose a **new, unused
file name** and leave the original alone:

```sh
export DATABASE_URL=another-learning-run.db
based migrate apply --database-url "$DATABASE_URL"
cargo run
```

PowerShell uses `$env:DATABASE_URL = "another-learning-run.db"` instead of
`export`. Do not delete an existing database as a hidden setup step. Stop all
readers/writers before moving database files or their SQLite sidecars, and use a
proper database backup for data you need to preserve. The starter ignores local
database files and `.env`; it does not remove them.

SQLite is a local-file starting point. Its concurrency, locking, and supported
schema changes differ from server databases; this example does not establish
server-style concurrency or arbitrary system SQLite support. The tested engine
and version boundary are in the [support policy](support-policy.md).

For the same initializer workflow against your own server, choose
`--dialect mariadb` or `--dialect postgres`, export `DATABASE_URL`, then apply and
run. No server is provisioned. See the deeper
[MariaDB](../examples/mariadb-quickstart/README.md),
[PostgreSQL](../examples/postgres-quickstart/README.md), and
[verified TLS](database-tls.md) guides for connection setup and larger scenarios.
The helpdesk remains an advanced application example, not a prerequisite.

## Separate verification

`make ci-initializer` runs the shared starter contract. `make ci-onboarding` runs
the separate [`ci/check-embedded-tutorial.py`](../ci/check-embedded-tutorial.py) rename smoke
and the standalone tutorial; the release gate uses extracted candidate tools.
It uses a fresh external consumer, retains existing row/owner/parent IDs across
migration, and verifies regenerated typed calls, formatting, linting, and output
freshness. Readers need none of its harness internals to run the commands above.
