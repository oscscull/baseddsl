# A small Rust application

This tutorial builds one Rust program with one model and one relation, runs a
typed mutation and query against SQLite, then renames a field without losing
data. It needs no database server.

## Create the project

[Install Based](installation.md), then create a project in a new directory:

```sh
based init items --mode embedded
cd items
based migrate apply --database-url local.db
cargo run
```

`based migrate apply` creates `local.db` and its tables. `cargo run` creates an
item and its parent, then prints them:

```text
created: {"id":"…","name":"Hello Based","parent":{"id":"…","name":"Parent"}}
read: [ … ]
lookup: not found in this owner's context
```

`Cargo.toml` pins the Based libraries to the Git commit of your `based` binary,
so the project builds anywhere, outside this repository too.

| File | Owner |
|---|---|
| `schema/item.bsl` | You: the model, its projection and its calls |
| `src/main.rs`, `src/database.rs` | You: wiring the schema and database into the engine |
| `src/demo.rs`, `src/session.rs`, `src/lookup.rs` | You: sample calls, context and error handling |
| `migrations/0001_init/` | Generated by `based init`; commit it and never edit it after applying |
| `based.toml`, `build.rs` | You: project settings and the client generation hook |

The typed client is generated, and never appears among your files: `build.rs`
writes it to Cargo's build directory under `target/` on every `cargo build`,
and `src/main.rs` includes it as `mod client`. See
[generated clients](generation.md).

## Read the schema

```bsl
scope Author (owner: uuid = $ctx.owner)

@scope Author
Item {
  id: Id
  name: text
  owner: uuid
  parent: Item?
  @index owner
}

shape ItemView from Item {
  id
  name
  parent { id, name }
}

mutation create_item(name: text, parent: Item?) -> ItemView scoped Author {
  create Item { name = $name, parent = $parent };
}

query items() -> ItemView[] scoped Author {
  list Item order (id);
}

query item_by_id(id) -> ItemView scoped Author;
```

`Item` has an optional `parent`, which is the relation. `ItemView` is what the
calls return: an item with its parent's ID and name. `create_item` is the
mutation and `items` the query.

`scope Author` makes every call take an owner as context, and the engine
filters reads and writes by it. Context comes from your host, never from the
caller's input:

```rust
let rows = api
    .items(client::ItemsInput {}, client::ItemsCtx { owner: session.owner() })
    .await?;
```

`src/session.rs` returns a fixed local owner; a real application takes it from
its authenticated session. `src/lookup.rs` asks for the created item as a
second owner and gets `Ok(None)`, because the item is outside that owner's
scope. Its `Err` branch prints the error's kind, code and status, which every call
can return, and passes the error on.

## Change the schema

Rename `name` to `title` in the stored table while keeping `name` in the
results. Replace `schema/item.bsl` with:

```bsl
scope Author (owner: uuid = $ctx.owner)

@scope Author
Item {
  id: Id
  title: text @was("name")
  owner: uuid
  parent: Item?
  @index owner
}

shape ItemView from Item {
  id
  name = title
  parent { id, name = title }
}

mutation create_item(name: text, parent: Item?) -> ItemView scoped Author {
  create Item { title = $name, parent = $parent };
}

query items() -> ItemView[] scoped Author {
  list Item order (id);
}

query item_by_id(id) -> ItemView scoped Author;
```

`@was("name")` makes the migration a rename, so existing values and parent IDs
are kept; a drop and add would lose them. `name = title` keeps the field name
in `ItemView`. Then plan, check and review the migration:

```sh
based check
based migrate gen . rename_item_title
based migrate verify
based migrate render . --number 2
```

`migrate gen` writes `migrations/0002_rename_item_title/`; `render` prints its
SQL so you can review it. Apply it and run the program again:

```sh
based migrate apply --database-url local.db
cargo run
```

`cargo run` rebuilds the client from the new schema; there is no separate
generation step. The earlier rows keep their names. Commit the schema,
`migrations/` and `Cargo.lock` together.

## Run again or start over

Each `cargo run` adds two more items. To start over, stop the program, delete
the database, then apply and run again:

```sh
rm -f local.db local.db-journal local.db-wal local.db-shm
based migrate apply --database-url local.db
cargo run
```

The reset only removes this tutorial's database files. Never delete a database
you did not create for the tutorial.

## SQLite in this tutorial

- `local.db` is a file. Relative paths resolve against the project directory,
  for the CLI and the program alike. Set `DATABASE_URL` to use another file.
- `:memory:` creates a new empty database for each process. A database applied
  with `based migrate apply` then disappears, so use a file, or
  [migrate on start](#migrate-on-start).
- SQLite allows one writer at a time. Let the program finish before migrating
  or deleting the file.

The same steps work on a server database: run
`based init items --mode embedded --dialect mariadb` or `--dialect postgres`
and export `DATABASE_URL` for a database you provide; drop `--database-url`
from the commands. See [connection configuration](configuration.md) and
[migrations](migrations.md).

## Ship one binary

The schema is compiled into the executable, so a bundled app needs no
`schema/` folder at runtime. `build.rs` checks it (a broken schema fails
`cargo build`) and embeds it:

```rust
mod schema {
    include!(concat!(env!("OUT_DIR"), "/schema.rs"));
}

let compiled = based_runtime::Compiled::from_sources(schema::MANIFEST, schema::SOURCES)?;
```

Without `based-build`, pass the manifest text and `(name, text)` pairs
yourself:

```rust
const SCHEMA: &[(&str, &str)] = &[("task.bsl", include_str!("../schema/task.bsl"))];
let compiled = Compiled::from_sources(include_str!("../based.toml"), SCHEMA)?;
```

`from_sources` runs the same check as `Compiled::load`: errors fail and cite
the embedded name, and warnings do not.

### Migrate on start

`build.rs` also embeds `migrations/` as `schema::MIGRATIONS`, so the app can
create or upgrade its own database without a migrations folder:

```rust
use based_runtime::migrate::{self, ApplyOpts};

let backend = based_runtime::SqliteBackend::open(&path)?;
let migrations = migrate::from_sources(compiled.dialect, schema::MIGRATIONS)?;
migrate::apply(&backend, compiled.dialect, &migrations, &ApplyOpts::default()).await?;
let engine = based_runtime::Engine::new(compiled, backend, based_runtime::id::UuidGen);
```

`cargo build` fails on anything `based migrate verify` rejects: a gap in the
numbering, an `up.mig` edited away from its `schema.snap`, or a schema change
no migration captures. Apply keeps the same `_based_migrations` ledger as
`based migrate apply`, so the two can manage the same database. An applied
migration edited later is refused, and destructive steps need
`ApplyOpts { allow_destructive: true, .. }`. `Dialect` is re-exported as
`based_runtime::Dialect` for code that names it directly.

## Choose the SQLite driver

`based-runtime` has two SQLite drivers with the same behaviour: pools,
transactions, binds, migrations, idempotency and errors.

| Feature | Backend | Driver | `libsqlite3-sys` |
| --- | --- | --- | --- |
| `sqlite` | `SqliteBackend` | sqlx 0.9 | 0.37.x |
| `sqlite-rusqlite` | `RusqliteBackend` | rusqlite 0.39–0.40 | 0.37.x or 0.38.x |

Cargo links one `libsqlite3-sys` per build, so pick the driver whose range
contains the one your application already uses. An application on rusqlite
0.40 uses `sqlite-rusqlite`:

```toml
based-runtime = { version = "0.1", default-features = false, features = ["sqlite-rusqlite"] }
```

`RusqliteBackend` has the same constructors as `SqliteBackend` (`in_memory`,
`open`, `open_with_pool`). `from_connection` and `from_connector` take
connections you configured, and `with_connection` runs your own rusqlite code
on the engine's connection. To include engine calls in your transaction, run
`BEGIN` on your connection and pass it to the generated `adopt_rusqlite`
(your crate's `sqlite-rusqlite` feature forwards to
`based-runtime/sqlite-rusqlite`); the calls fail if no transaction is open. Both features bundle SQLite, version
3.51.3 or later.
